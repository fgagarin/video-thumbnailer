# Golden reference results (Python implementation)

These files capture what the Python FrameCover core (`src/framecover/core/`)
produces for a fixed set of synthetic inputs. The Rust port in
`crates/framecover-core` is checked against them; deliberate fixes since the
port are listed as intentional deviations in `tests/golden.rs`.

The Python implementation and the generator script were removed when the Rust
version replaced it. To regenerate, check out the last Python release
(`git checkout v0.1.0`, plus `scripts/golden/` from commit `d6e1d22`).

Generated by `scripts/golden/generate_golden.py`; the tool versions used are in
`_environment.json` (FFmpeg n8.1 from `vendor/ffmpeg`, PyAV 19.0.2, mutagen
1.48.1, Pillow 13.0.0).

## Regenerating (from a Python checkout)

```sh
uv sync --extra dev
uv run python scripts/golden/generate_golden.py            # all cases
uv run python scripts/golden/generate_golden.py --only save_mp4 resave_mp4
uv run python scripts/golden/generate_golden.py --ffmpeg path/to/ffmpeg.exe
```

The script finds ffmpeg via `--ffmpeg`, then `FRAMECOVER_FFMPEG` or
`IMAGEIO_FFMPEG_EXE`, then `vendor/ffmpeg/` in the checkout or any parent
directory (so it also works from a nested git worktree). `ffprobe` must be next
to it. The binary is exported as `IMAGEIO_FFMPEG_EXE`, so the Python writer and
converter run the same FFmpeg build as the Rust port. **PyAV uses its own bundled
libav\*** for loading and frame extraction, not that binary.

The output is deterministic: two runs give byte-identical files. Only the GUI is
skipped. Everything else (`PyAVVideoLoader`, `PyAVFrameExtractor`,
`FormatDispatchThumbnailWriter` through `save_copy`, `FFmpegVideoConverter`) is
the real code.

## Fixtures

These are the same recipes as `tests/conftest.py` and
`crates/framecover-core/tests/common/mod.rs`:
`testsrc=size=320x240:rate=25:duration=5` plus `sine=frequency=440:duration=5`.

- mp4/mov/mkv/avi/flv: `-c:v libx264 -c:a aac -pix_fmt yuv420p`
- webm: `-c:v libvpx-vp9 -c:a libopus -b:v 200k`. No pix_fmt is set, so the
  stream is **VP9 Profile 1 / gbrp**, not yuv420p. The conftest recipe does the
  same.
- with_thumb: base mp4 plus a blue 320x240 JPEG (`-q:v 2`) muxed as
  `-disposition:v:1 attached_pic`

The frame is always extracted with `PyAVFrameExtractor` at **2000 ms**. Second
saves use **3000 ms** on the produced copy. The destination is always
`<stem>-thumbnail<ext>` next to the input.

## Cases

| Case | What it covers |
|------|----------------|
| `save_mp4` | H.264/AAC MP4: concat fast path (one preview frame prepended, +40 ms shift), mutagen `covr` and freeform tags |
| `save_mov` | MOV: the non-`.mp4` extension forces the full re-encode path; output muxed with `-f mp4` (brand `isom`) |
| `save_mkv` | MKV: `-attach` of `cover.jpg` (`image/jpeg`) |
| `save_mkv_two_audio` | MKV with 2 audio tracks: default stream selection keeps only **1** audio track (data loss) |
| `save_avi` | AVI: plain `-c copy` remux, no cover; success with an informational `error_message` |
| `save_flv` | FLV: no ffmpeg call; the copy is published unchanged; success with an informational `error_message` |
| `save_webm` | WebM: same as FLV |
| `save_mp4_with_thumb` | MP4 with an attached_pic but no FrameCover tags: full re-encode; the old cover is replaced |
| `resave_mp4` | Save MP4, then save the copy again: replace-existing-preview path (`noise=drop='eq(n,0)'` strip plus concat, no `-itsoffset`, shift 0) |
| `resave_mov` | Save MOV twice: full re-encode both times |
| `resave_mkv` | Save MKV twice: the old attachment is dropped (default stream selection) and one new `cover.jpg` is attached |
| `save_mp4_yuv444p` | H.264 High 4:4:4 / yuv444p: concat-ineligible (profile and pix_fmt), full re-encode |
| `save_mp4_hevc` | HEVC (`hvc1`): concat-ineligible (codec), full re-encode to H.264 (the Rust port takes the HEVC fast path, see the deviations) |
| `save_mp4_av1` | AV1 (libaom, 160x120): concat fast path with a libaom preview frame |
| `convert_ts` | MPEG-TS H.264/AAC to MP4: `-c copy` remux accepted (no transcode) |
| `convert_mpg` | MPEG-PS MPEG-2/MP2 to MP4: remux succeeds but is concat-ineligible, so it is transcoded with libx264/AAC |
| `convert_wmv` | ASF WMV2/WMAv2 to MP4: remux fails (exit -22), `-encoders` probe, then a libx264/AAC transcode |

## File layout

`<case>.json` is the behavioural summary:

- `fixture`: the input's `file_name`, `probe` (ffprobe summary), `load`
  (VideoFile from `PyAVVideoLoader`), `reencode_reason`, and `mp4_tags` for
  .mp4/.mov.
- `save` / `first_save` / `second_save`: `position_ms`, `extracted_frame_size`,
  `destination`, `result` (ApplyResult: `success`, `error_code`,
  `error_message`, `duration_shift_ms`, `output_path`), and
  `new_files_in_directory` (catches leaked temp files; it should list only the
  output and its receipt). Then `output` (same shape as `fixture`, reloaded
  after the save) and `receipt` (file name, JSON keys, version; hashes are
  omitted).
- `convert`: `returned_path`, `error`, `progress_stages`,
  `new_files_in_directory`, `output`, and `concat_ineligibility_reason` of the
  result.
- `mp4_tags`: from mutagen. `frame_number` and `position_ms` are the ASCII
  values of `----:com.apple.iTunes:video-thumbnailer-frame-number` and
  `-position-ms`. `covr` gives the count, imageformat (13 = JPEG) and decoded
  size. `keys` lists all ilst keys (`©too` comes from the ffmpeg muxer).

`<case>.commands.json` lists every `subprocess.run` argv the Python writer or
converter ran, in order, with the signed return code. Placeholders:

- `<FFMPEG>` is the ffmpeg executable.
- `<WORK>` is the per-case temp directory, shown with `/` separators.
- `XXXXXXXX` stands for the 8 random characters `tempfile` adds:
  - `.vt_cover_XXXXXXXX.jpg`, `.vt_frame_XXXXXXXX.png`,
    `.vt_preview_XXXXXXXX.mp4`, `.vt_concat_XXXXXXXX.txt` and
    `.vt_stripped_XXXXXXXX.mp4` are the writer temps.
  - `.vt_XXXXXXXX.tmp` is the `atomic_replace` temp.
  - `.<stem>.save-XXXXXXXX<ext>` is the `save_copy` staged copy.
  - `.<stem>-XXXXXXXX.mp4` is the converter temp.

Concat invocations also have `concat_manifest`, the manifest file's lines. Entries
with a `marker` key separate the first and second save.

## Comparing from Rust

**Exact match:**

- ApplyResult `success`, `error_code`, `duration_shift_ms`, and
  `error_message` when it is informational (AVI/FLV/WEBM). Error messages that
  contain paths and stderr are compared by `error_code` only.
- `reencode_reason`, `concat_ineligibility_reason` (the strings are shown in
  the UI) and converter `progress_stages`
- `load.format`, `width`, `height`, `has_existing_thumbnail`,
  `existing_thumbnail_size`, `thumbnail_frame_number`, `thumbnail_position_ms`
- Per stream: `codec_type`, `codec_name`, `profile`, `pix_fmt`, `width`,
  `height`, `time_base`, `attached_pic`, `tags_filename`, `tags_mimetype`,
  `sample_rate`, `channels`
- `nb_streams`, stream order, `format_name`, `major_brand`
- `nb_frames` for MP4/MOV video. This is how a prepended frame is detected:
  125 becomes 126, and stays 126 after a replace.
- `mp4_tags.frame_number`, `position_ms`, `covr` (count, format, size), and the
  freeform/`covr` keys
- Receipt `file_name`, `keys` and `version`
- `new_files_in_directory`
- Commands: the argument vectors with placeholders, the number and order of
  invocations, and the concat manifest. A Rust port that calls ffmpeg through
  an extra wrapper can drop or add `-hide_banner`/`-loglevel`/`-nostdin`, but
  must say so explicitly in its test. Return codes should match on success
  (0) and failure (non-zero).

**With tolerance:**

- `duration_ms` (format, stream and `load.duration_ms`): ±1 frame (40 ms at
  25 fps). AAC priming and edit lists move these by a few ms.
- `start_time_ms`: ±1 frame. For example, the concat output's audio starts at
  16 ms, not 40.
- `frame_step_ms`: exact, except that it is derived from `avg_frame_rate`. For
  concat outputs that value is `1575/62` (step 39); see below.
- `avg_frame_rate`: exact for direct encodes. For concat outputs, compare the
  derived step only.
- `nb_frames` for audio, and `compatible_brands`: informational only.

## Behaviour worth knowing when porting

These are observed in the Python implementation and recorded as-is in the
goldens. Decide deliberately whether the port matches them or fixes them.

1. **Frame rate drift after the concat fast path.** After one prepended frame,
   the MP4's video stream reports `avg_frame_rate = 1575/62` (≈25.40 fps) and
   a stream duration of 4960 ms, even though it holds 126 frames at 40 ms. As a
   result:
   - The reloaded VideoFile has `frame_step_ms = 39` and `duration_ms = 4960`.
   - A second save writes `frame_number = round(3000/39) = 77`, where the true
     frame is 75.
   - The second save encodes the preview with `-framerate 1575/62` and the
     manifest uses `duration 0.0393650793651` in place of 0.04.
   - The first save writes `frame_number` with the original 40 ms step (51),
     so the tag and the reloaded step disagree.

   AV1 concat output does not drift (5040 ms, step 40).
2. **The full re-encode overwrites frame 0** (`overlay ... enable='eq(n,0)'`)
   rather than prepending a frame, so the first real frame is lost. In
   exchange, `duration_shift_ms` is 0 and the tags hold the unshifted position
   (50 / 2000).
3. **MOV always takes the full re-encode path**, every time it is saved
   (generational loss), and is muxed with `-f mp4`, so `.mov` outputs carry
   brand `isom`. `write_mp4_covr` is false for MOV, but the mp4 muxer turns the
   attached_pic stream into a `covr` atom anyway. The freeform tags are also
   written to MOV by mutagen.
4. **MKV and AVI remux with ffmpeg default stream selection** (no `-map`), so
   extra audio and subtitle tracks are silently dropped. In `save_mkv_two_audio`
   the input has video and two audio tracks; the output has video, **one**
   audio track and the new cover. For MKV it
   also means the previous cover attachment is dropped, which is why re-saving
   does not accumulate attachments.
5. **WebM and FLV saves do nothing** apart from publishing an unchanged copy
   and a receipt. They return `success=True` with an `error_message` that
   claims "Linux file manager icon updated via XDG cache", which is not true on
   Windows or through `save_copy`. AVI also returns success with a non-null
   `error_message`.
6. **MKV, WebM, AVI and FLV keep no frame metadata**: thumbnail tags are read
   and written only for MP4/MOV. `load.thumbnail_*` stays null.
7. `video_with_thumb` (a foreign cover with no FrameCover tags) is not eligible
   for the replace path, because that needs `thumbnail_position_ms`. It falls
   back to a full re-encode with the reason "An attached-picture video stream
   is already present."
8. **The converter checks concat eligibility after remuxing.** MPEG-2 remuxes
   into MP4 successfully (return code 0 in `commands.json`) and is only then
   rejected and transcoded, so the work of that remux is wasted. WMV2 fails the remux with
   exit -22, which Windows reports as `4294967274` and the goldens normalise to
   signed.
9. **Loader duration sources differ by container:**
   - MP4/MOV use the video *stream* duration (`stream.duration * time_base`).
   - MKV/WebM/FLV have no stream duration and fall back to the container
     duration (5023, 5008 and 5080 ms for 5 s fixtures).

## Intentional deviations of the Rust port

Some of the behaviours above are bugs that were fixed after the port reached
parity. The golden files are **not** regenerated: `tests/golden.rs` patches
exactly the expected values each fix changes (`apply_intentional_deviations`,
with a comment per fix) and compares everything else against Python.

- Behaviour 1 (frame rate drift): the concat output's leading DTS are
  repaired with `-bsf:v:0 setts=…`, so outputs keep the source frame rate and
  duration + one frame. The loader also reads already-drifted files with
  `r_frame_rate` (see `Stream::effective_rate`).
- Behaviour 2 (re-encode overwrites frame 0): the re-encode inserts the poster
  as an extra first frame (`concat` filter), shifts audio/subtitles with
  `-itsoffset`, reports `duration_shift_ms` 40 and shifted tags (2040 / 51),
  and forces a keyframe on the first source frame. A re-save trims the old
  preview (or strips it by stream copy when the file is concat-eligible).
- Behaviour 3 (MOV always re-encoded as `isom`): `.mov`/`.m4v` take the
  concat fast path (or the re-encode) muxed with `-f mov`, so outputs keep
  brand `qt  `; the cover is written as a `covr` item. `save_mov` and
  `resave_mov` expect the `save_mp4`/`resave_mp4` commands on `.mov` paths.
- Behaviour 4 (default stream selection): MKV and AVI remuxes use `-map 0`;
  `save_mkv_two_audio` keeps both audio tracks. MKV re-saves drop only
  cover-named attachments (`cover.jpg`, `cover.png`, `cover.jpeg`,
  `folder.jpg`) before attaching the new `cover.jpg`.
- Behaviour 5 (misleading messages): WebM/FLV/AVI successes carry
  `thumbnail_writer::no_cover_art_note`, which makes no platform claim.
- Behaviour 8 (wasted remux): the converter checks the source's codec,
  profile, pixel format and dimensions first
  (`thumbnail_writer::remux_ineligibility_reason`); `convert_mpg` and
  `convert_wmv` encode without attempting the remux.
- HEVC fast path (not a Python behaviour, a new feature): HEVC Main/Main 10
  sources are concat-eligible, so `save_mp4_hevc` encodes a libx265 preview
  frame (`hvc1`, the source's colour range and chroma siting) and stream
  copies the source like `save_mp4`; the output stays HEVC Main with 126
  frames and no `reencode_reason`. The source's `hvc1` sample entry is put
  back afterwards (`sample_entries`, no ffmpeg command).
